# How I Document My Engineering Work

I am using this file to remind myself how I should document my own work.

## 1. Start with the purpose

Before running commands, I should know what I am trying to learn or prove.

Example:

> I want to understand how Linux processes are created, managed and terminated.

## 2. Explain the concept in my own words

I should write what I understood, not copy a textbook definition.

I normally use:

- What is it?
- Why does it matter?
- How does it work?
- How does it connect to the bigger system?

## 3. Record the experiment

I should record the commands I actually ran.

I should not add commands just because I saw them somewhere.

## 4. Record what happened

I should write the important output or result.

If the output is long, I can keep the important part and explain what it showed.

## 5. Record what I learned

This is more important than the command itself.

I should explain what the experiment proved to me.

## 6. Record problems honestly

If something failed, I should record:

- what I expected
- what actually happened
- what I checked
- what caused the problem
- how I fixed it

A failure is useful evidence when I understand it.

## 7. Separate completed work from planned work

I should use clear wording:

- Completed
- Practiced
- Tested
- In progress
- Planned

I should not say I built or mastered something if I have not actually done it.

## 8. Connect the lab to engineering

At the end I should ask:

> Where would I use this in a real system?

This helps me move from learning commands to understanding systems.

## 9. Git evidence

For a meaningful milestone, my process is:

LEARN → BUILD/CONFIGURE → TEST → OBSERVE → UNDERSTAND → DOCUMENT → VERIFY → COMMIT

I should commit meaningful milestones instead of making random commits for every small command.
